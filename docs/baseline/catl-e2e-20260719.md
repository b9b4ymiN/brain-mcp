## 1. The three production bugs found (root cause, not symptom)

All three were latent — the extraction pipeline had **never run against a real
provider before 2026-07-19** (the `[provider]` wiring fix landed the same day
in commit `7cb0604`). Each one surfaced only on first live-fire use.

### BUG #1 — MCP tool-call timeout hardcoded at 30 s

- **Symptom:** `brain_extract` returned "AI response was not valid JSON after
  bounded repair (discarded): EOF while parsing a value at line 1 column 0"
  with an empty response body.
- **Root cause:** `src/mcp/mod.rs:443` wrapped `tools::call` in
  `tokio::time::timeout(Duration::from_secs(30), ...)`. Reasoning models
  (glm-4.6 / glm-5.2) routinely take 15-30 s of `reasoning_content` before
  emitting the final `content`; an extraction prompt with a 4 KB chunk took
  ~119 s end-to-end. The MCP layer cancelled the call mid-flight, and the
  downstream parser received an empty string that looked like a malformed
  JSON response.
- **Fix:** new `[serve] mcp_tool_call_timeout_secs` config field
  (default **300 s**). `McpServer::with_tool_call_timeout(Option<Duration>)`
  builder. `0` disables the timeout. Wired through `serve()` in `server.rs`.
  The error message now reports the actual timeout value that fired
  (`"tool call timed out after 300s"`) instead of a hardcoded string.

### BUG #2 — Provider `reqwest` timeout hardcoded at 60 s

- **Symptom:** even after BUG #1, `brain_extract` returned
  `error: provider error: Timeout` (provider.rs's `ProviderError::Timeout`).
- **Root cause:** `src/provider.rs::ReqwestTransport::new()` set
  `.timeout(Duration::from_secs(60))` on the reqwest client. A single ~4 KB
  CATL chunk measured **119-206 s** wall time end-to-end against Z.ai
  glm-4.6 (live curl with the real extraction prompt + `response_format:
  json_object`). Three retry attempts × 60 s each all timed out.
- **Fix:** new `[provider] timeout_secs` config field (default **600 s**).
  `ReqwestTransport::with_timeout(Duration)` + `ZaiHttpAdapter::with_timeout(...)`
  constructor (mock-injected tests still go through `with_transport`, so the
  18+ existing tests that pin the retry/timeout-error classification are
  untouched). `0` disables the timeout at the reqwest layer (debug only).

### BUG #3 — Strict `parse_candidates` rejected the whole batch on a single bad claim

- **Symptom:** `error: AI response did not match the expected claims schema:
  missing field \`value\``. Reproduction showed the model usually emitted 27
  well-formed claims, occasionally omitting `value` on one claim after a long
  `reasoning_content`. Strict `serde_json::from_value` rejected the whole
  batch, throwing away 26 good claims.
- **Root cause:** reasoning-model output is **non-deterministic**. A
  strict-by-construction parser that errors on any malformed entry treats
  one model hiccup as a total failure. Live evidence: the same chunk
  produced 0/27 malformed on one run, then 1+/27 on another.
- **Fix (two parts):**
  1. **Lenient parser** (`extraction.rs::parse_candidates`): per-claim
     `serde_json::from_value` inside a loop; skip malformed entries (logged
     at warn level by the caller). Only error if NOTHING parses or the
     top-level `{"claims": [...]}` shape is wrong. Null `value` also skipped.
     New unit tests: `parse_candidates_skips_a_malformed_claim_but_keeps_the_rest`,
     `parse_candidates_handles_a_null_value_gracefully`. Existing
     `parse_candidates_rejects_a_claim_missing_required_fields` kept (asserts
     the all-malformed case still errors).
  2. **Prompt v2** (`EXTRACTION_PROMPT_VERSION = "d3-extraction-v2"`):
     re-emphasized "EVERY claim object MUST contain ALL seven fields" and
     "if you cannot fill every field, OMIT that claim rather than emitting
     a partial object". This reduces how often the leniency path is hit;
     it does not replace it.
