| Metric | Value | Notes |

| Proposals with ≥1 conflict | 0 | Correct — see below |
| Conflict kind distribution | `{}` | — |

**Why 0 conflicts is correct:** The current inbox has exactly one
duplicate `(subject, predicate)` key group — `("CATL", "customers")` —
between two proposals whose values are a JSON list `["Tesla", "BMW",
...]` and a short summary string `"multiple OEMs (Tesla, BMW, MB...)"`.
Neither value parses as f64 (so HardValue can't fire) and the two
serialized JSON values aren't string-equal (so Duplicate can't fire).
Cross-predicate tension like `¥361 vs ¥447.6` is intentionally **not**
flagged here — those have different predicates (`current_case_price` vs
`dcf_price_per_share`) and belong to Phase 1.7 C4 ontology work.

The detection path is wired and exercised end-to-end on real data. The
19 module unit tests cover HardValue (numeric rel_diff > 0.1% including
¥/$/%/B/M/K normalization), Duplicate (identical value), threshold
boundary (rel_diff = 0.001 → no flag), pending-vs-confirmed comparison,
non-comparable-value graceful skip, and scope-key bucketing.

## 📦 What shipped

### C1 — Evidence Snippet (`src/snippet.rs`)

- Replaces 3000+ char chunk dump with ±200 char value-anchored window
  snapped to whitespace, hard-capped at 600 chars
- `<mark>` highlight rendered in frontend (`web/console/src/pages/Inbox.svelte`)
  via plain `{prefix}<mark>{middle}</mark>{suffix}` interpolation —
  XSS-safe by construction (no `{@html}`)
- "Value not found in source — first 300 chars:" honest fallback when
  the LLM-inferred value isn't present in the span
- Multi-span: primary span + collapsed `additional_sources` list of
  remaining rendition IDs
- New `src/snippet.rs` pure module (19 unit tests, 0 I/O)
- 5 additive fields on `EvidenceSummary` (`value_located`, `value_offset`,
  `value_len`, `excerpt_truncated`, `additional_sources`) — all
  `#[serde(default)]` for backward compat

### C2 — Same-predicate Conflict Detection (`src/inbox_conflicts.rs`)

- Replaces misleading "N current confirmed claims in scope" (always 0
  because of confirmed-only filter) with real detection across
  pending + confirmed (active + future + past) claims
- **C1 HardValue** (Warning): same `(domain, subject, predicate)`,
  numeric values, `rel_diff > 0.1%`
- **C2 Duplicate** (Info): same `(domain, subject, predicate)`,
  structurally equal value
- Numeric normalizer handles ¥/$/€/£/฿ prefixes, thousands separators,
  and B/M/K suffix multipliers
- New `src/inbox_conflicts.rs` pure module (19 unit tests, 0 I/O)
- Embedded in `InboxProposal` payload (`src/api.rs` inbox handler) —
  **no new endpoint**
- Frontend: badge on list row + expandable peers panel
  (`web/console/src/pages/Inbox.svelte`)

## 🔬 Research ที่ใช้ตัดสินใจ (Don't reinvent the wheel)

1. **Google Search / GitHub code search snippet shape** — ±200 chars
   around the match, snapped to whitespace, hard cap. Used by every
   production search UI the user already trusts.
2. **LlamaIndex `SentenceWindowRetriever`** — same ±window pattern for
   RAG; we apply it post-hoc to a chunk the LLM already chose.
3. **WikibaseQualityConstraints + SHACL** — bucket-by-key + pairwise
   comparison within bucket pattern for constraint checking. Drives the
   O(M·K) complexity choice (M buckets × K avg bucket size) over the
   naive O(N²) pairwise across all proposals.
4. **spaCy POS head-noun membership** (carried over from Phase 1.5) —
   predicate-level conflict detection uses simple scope keys today;
   Phase 1.7 will add a predicate ontology to catch cross-predicate
   tension (`price × shares ≠ market_cap`).

## 🔐 Security

- ✅ Snippet rendering uses plain Svelte interpolation (`{...}`, not
  `{@html}`) — XSS-safe by construction. The `<mark>` wrapper is built
  from char offsets in TypeScript, never from raw span text.
- ✅ Conflict detection consumes already-loaded read types — no new
  SQLite surface, no new SQL injection vectors.
- ✅ Numeric normalizer uses a single anchored regex; no ReDoS surface
  (input is bounded by `EvidenceSummary` size limits already enforced
  upstream).
- ✅ No new outbound HTTP, no new file I/O, no new subprocess.
- ✅ `.env` was loaded via `set -a && source .env && set +a` for the
  Docker smoke test; credentials were never echoed.

## 🎓 Lessons learned

1. **Pure module TDD paid off again** — same pattern as Phase 1.5
   (Subject Validator). Splitting `snippet.rs` and `inbox_conflicts.rs`
   as pure functions with no I/O let us write 38 unit tests in isolation
   before touching any store code, then wire into `evidence_for()` and
   the inbox handler with zero surprises.
2. **`cargo clippy -D warnings` caught a real lint in our Phase 1.6 code**
   — the inbox handler had a nested `if let Ok(..) { if let Ok(..) {`
   that collapsed into `if let Ok(..) && let Ok(..) {`. Clippy was
   right; the chained form is clearer.
3. **Live 0-conflicts result needed investigation** — at first glance
   "0 conflicts across 181 proposals" looks like the wiring is broken.
   Inspecting the data confirmed only one duplicate scope-key group
   exists, and its values are non-numeric and non-equal. The detection
   is correct; the data simply has no in-scope conflicts. The 19 unit
   tests + 4 integration tests cover the algorithm; the live endpoint
   proves the wiring.
4. **Live 58% `value_located=true` is honest, not a bug** — many
   LLM-inferred values use unit prefixes or range phrasings that don't
   match the source span verbatim. The 42% fallback path with explicit
   "Value not found in source" prefix is the right UX: don't lie about
   where a value came from.
5. **Don't `git add -A` on a tree with screenshots** — one slip during
   Task 14 fmt commit swept 525 untracked PNGs and `graphify-out/`
   artifacts into the commit. Used `git reset --soft HEAD~1` +
   selective `git add <files>` to recover. The Phase 1.5 pattern of
   always naming files explicitly in `git add` is the right one.
